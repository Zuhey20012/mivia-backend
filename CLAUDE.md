## What this is

Malvoya is a hyperlocal fashion marketplace for Finland: people buy, rent and return clothes, and local couriers deliver them. One Node/TypeScript API serves three Flutter apps (customer, vendor, courier) and a React admin panel. The project is pre-launch: there are no real vendors, couriers or customers yet, and the production database contains only test accounts.

## Backend architecture

- `src/index.ts`: the Stripe webhook router is mounted **before** `express.json()`, because it needs the raw body. Courier routes are mounted before order routes, and every `:id` route uses `(\\d+)` so paths like `/orders/available` are never captured. `trust proxy` is set to 1 for Render.
- Module pattern: `src/modules/<name>/{routes,controller,service,schema}.ts`. Zod validates every body. Responses are `{ ok: true, … }` or `{ ok: false, error }`. Services throw `AuthError` or `OrderError` with an HTTP status; controllers map them.
- Auth: 15-minute access JWT (`typ: "access"`, HS256) plus a 7-day single-use refresh JWT, stored **SHA-256-hashed** in `RefreshToken`. All login paths go through `modules/auth/session.ts#issueSession`. Register never touches existing accounts. Verified sign-ins (Google, Apple, Firebase phone, one-time code) never open an account made by `/register` (bcrypt password, email/phone never proven); they get 409 from `auth.service.ts#assertVerifiedSignInAllowed`, so nobody can pre-register someone else's address. To use Google with such an account, the signed-in user links it (`POST /auth/google/link`, a "Google account" tile in each app's account settings): `User.googleSub` then opens that account on Google sign-in whatever its email, and sessions report `user.googleLinked`. Only password accounts can unlink (`DELETE /auth/google/link`); account deletion clears the link. Roles: `CUSTOMER | VENDOR | COURIER | ADMIN`. `ADMIN` is never self-assignable. Social sign-in (Google, or Firebase phone/Apple) accepts a `role` for **new** accounts only.
- `Courier` is a separate table linked by `Courier.userId`. Couriers need `isApproved` (set by an admin) before they get jobs. `modules/orders/access.ts#getOrderRelation` is the single authorisation check deciding who may see or act on an order (customer / vendor / assigned courier / admin). Both HTTP and sockets use it.
- **Order lifecycle** (`orders.service.ts` `TRANSITIONS`): `PENDING` (created, awaiting payment) → the **Stripe webhook** sets `paymentStatus=SUCCEEDED` (the only place an order becomes paid) → the vendor accepts (`CONFIRMED`) or declines (`CANCELLED` with an automatic refund) → `PROCESSING` (sets `Order.readyAt`: the store has it ready) → the assigned courier moves it to `SHIPPED` (picked up) and then `DELIVERED` (sets `deliveredAt`). Stock is reserved with conditional decrements at creation and restocked on cancellation. Money is integer cents in EUR. `utils/pricing.ts#deliveryFeeForDistance` (env `DELIVERY_FEE_BASE_CENTS`/`_BASE_KM`/`_PER_KM_CENTS`/`_MAX_CENTS`, defaults 190 c for 1.5 km + 50 c/km, max 690 c) is used by both the store list and checkout, so the displayed fee always matches the charged one.
- Returns (since 2.10.0): `Return.storeNote` (the store's words, separate from the customer's `conditionNote`; required for REJECTED, accepted as the explanation of a deduction). Creating a return pushes the store owner (`orders` channel, data `{type:"return", returnId, orderId}`) and emits `return:new` to `store:`; APPROVED/REJECTED push the customer. The customer's `/returns` items carry `store {name, address, phone}`.
- Store payouts are held while any return on the order is open (`REQUESTED`/`APPROVED`/`IN_TRANSIT`/`RECEIVED`); `processDuePayouts` skips them until the return is refunded (payout reduced) or rejected.
- Returns: the 14-day withdrawal window counts from `deliveredAt`. `PATCH /returns/:id/status` with `REFUNDED` issues a real Stripe refund. Since 2.8.0 `POST /returns` takes optional `items: [{orderItemId, quantity}]` (`ReturnItem`; absent = what is left of the order; returns from before have no rows and cover the whole order); quantities are checked against bought − earlier non-rejected returns. `orders.service.ts#refundPlan`: a partial return refunds Σ unit × qty less a proportional share of the promo discount; the return that completes the order refunds everything paid for the sale (incl. delivery, service and small-order fees, less discount) minus what earlier returns refunded or deducted, so returning in parts totals the same as at once. Only the returned items are restocked; `adjustStorePayoutForRefund(orderId, refund, goodsCents)` takes back the returned goods value less the order's own commission rate (`commissionCents / subtotalCents`). Payloads: `items [{orderItemId, quantity, name, unitCents}]`, `refundCents` (null until refunded), `expectedRefundCents`. Deleting an account **anonymises** the user and keeps orders, as the Accounting Act requires.
- Dispatch (`services/dispatchService.ts`): after the vendor accepts, the order is offered via socket to approved online couriers within 7.5 km, nearest first; otherwise to all online couriers. The first courier to accept wins (conditional update). Nothing is auto-assigned. Offers, `GET /orders/available` and `GET /orders/courier/mine` carry `courierPay` (breakdown + `explanation {en, fi}` + one-sentence `summary`).
- Sockets (`lib/socket.ts`): JWT handshake. Rooms are joined only after `getOrderRelation` passes. `user:`, `store:`, `courier:` and `couriers` rooms are joined server-side from the token (handlers are registered before that async lookup, so an early `chat:join` is never lost). Only the assigned courier can emit a location for an order. Chat is stored (see Order chat below).
- Notifications (`services/notificationDeliveryService.ts`): the server sends email/SMS only on real events (payment confirmed, status changes, OTP). Without SMTP/Twilio configured, production sends nothing and development logs the message (never the text of code emails: `sendEmail(..., { sensitive: true })`). Emails are HTML-escaped; the seller is named as the seller, not Malvoya.
- **Language of pushes and emails** (since 2.10.0, `lib/i18n.ts`): every server text is written next to its use as `t(en, fi)` (`joinText`, `euros`, `lowerFirst` helpers) and picked per recipient from `User.locale` ("fi" | "en", null = English). `pushToUsers` groups devices by their user's locale; email templates look the locale up by address (`localeOfEmail`). The `auth` middleware stores the app's `Accept-Language` (fi → "fi", anything else → "en", none/`*` → unchanged), writing only when it changes; `PATCH /me {locale}` sets it explicitly.
- **Session state** (`middleware/auth.ts`): after the JWT check, `auth`/`optionalAuth` read `User.isActive`, `tokensValidAfter` and `locale` (cached 30 s per user and instance; `forgetSessionState` clears it on reset, ban, deletion, PATCH /me). Inactive accounts and access tokens issued before `tokensValidAfter` get 401, so a password reset/change, ban or deletion ends other devices at once on this instance and within 30 s elsewhere.
- OTP codes are stored hashed in the `OtpCode` table.
- **Passwords** (since 2.10.0, `modules/auth/passwordReset.ts`): `POST /auth/password/forgot {email}` always answers `200 {ok:true}` for a well-formed address (503 when email cannot be sent: production without SMTP) and does the work after responding, so neither status nor timing reveals accounts; limits: 10/15 min per IP and 3/hour per address (hashed key, account-independent). Accounts with a password get a 6-digit code (OtpCode target `pwreset:<email>`, SHA-256 like sign-in codes, 15 min, 5 tries, rejected by `/auth/otp/verify`); Google/phone/code accounts get a "no password needed" note. `POST /auth/password/reset {email, code, password}` (400 wrong/expired) sets the hash, `tokensValidAfter` and revokes all refresh tokens. `POST /auth/password/change {currentPassword, newPassword}` (signed in, 400 wrong current) does the same but returns a fresh session. Sessions and `GET /me` carry `hasPassword`.
- **Agreements** (since 2.10.0): `/auth/register` requires `acceptTerms: true` for VENDOR/COURIER (400) and stores `termsAcceptedAt` + `termsVersion` (`<file>@<first 12 hex of SHA-256 of the text>`).
- **Legal versions and acceptance records** (since 2.11.0, `modules/legal/{legalDocs,agreements,admin.legal}.ts`): `LegalVersion` holds every published text (docs `terms`, `seller-terms`, `courier-agreement`, `privacy`). The first version of each is created at start-up from `legal/*.md` (effective at once); later file changes do nothing until an admin publishes them (`POST /admin/legal/:doc/publish {effectiveAt, summaryEn, summaryFi, legalObligation?, reason?}`; notice seller terms/courier agreement ≥ 15 days, terms/privacy ≥ 0, `legalObligation` bypasses with an audited reason; 409 when unchanged or one is already pending; push + email to everyone the doc binds). `/legal/:doc` renders the version in force; `/legal/:doc/versions` (JSON, also under `/api/v1`) and `/legal/:doc/v/:version`. `AgreementAcceptance` (unique user+doc+version; IP /24 or /48, UA ≤ 200, `X-App-Version`, method) is written at registration (customers: terms + privacy) and by `POST /me/agreements/accept` (current or pending version only, idempotent, emails a copy; `GET /me/agreements`, `/me/agreements/:id/copy`, `/copy/link` 10-min signed link). `requireAgreement()` returns 428 `AGREEMENT_REQUIRED` for POST /orders and /rentals, a store's CONFIRMED, visible product create/publish and import publish, courier going online and accept; privacy is never blocking. Kept for the account's life + 10 years (scheduler `agreement-retention`).
- **Business check and onboarding** (since 2.11.0): `stores/businessCheck.ts` validates the Y-tunnus check digit (400) and looks it up at `https://avoindata.prh.fi/opendata-ytj-api/v3/companies?businessId=` (5 s timeout, 12 h cache; `PRH_API_TEST_HOST` test only) → `Store.businessCheckStatus` matched|name_mismatch|not_found|inactive|unavailable; never approves. `POST /admin/vendors/:id/business-check` re-runs it. `onboarding/onboarding.ts`: `GET /stores/my/onboarding`, `GET /courier/me/onboarding`, `PATCH /courier/me {vehicleType, phone}`, `POST /courier/me/disclosures {locationDisclosure:true}`; when everything but approval is done, `readyForApprovalAt` is set once, admins get push + email, and System lists it.
- Errors: new modules throw `ApiError(message, status)` from `lib/errors.ts` and reply through `sendError`; the message must be safe to show users.
- **Media** (`lib/cloudinary.ts`, `modules/media`): the apps upload straight to Cloudinary with a one-time signature from `POST /media/sign`. Each kind (`product_image`, `store_image`, `drop_video`, `drop_image`, `delivery_proof`, `avatar`) has an owner-scoped folder prefix; anything the apps send back is checked with `verifyOwnedUpload` (Cloudinary's response signature + prefix). Apps never send raw URLs of their own; product/store image URLs must be in the owner's folder. Delivery proofs are `authenticated` (private, signed URLs) and purged after 30 days. The secret never leaves the server. Without `CLOUDINARY_*` env vars uploads return 503.
- **Product videos** (`modules/products/productVideos.ts`, `ProductVideo`): up to 3 videos of 60 s per product, uploaded as `product_video` (signed, HLS via the same Cloudinary eager/notify pipeline as drops; the scheduler's `product-video-processing` job is the safety net). `presentProduct` returns READY videos only (owners also see PROCESSING/FAILED with `status`); every product query uses `productInclude`. Customer app: `widgets/product_gallery.dart` (video first, then photos; full-screen viewer with pinch zoom) and `widgets/product_video_player.dart`; one app-wide sound switch in `core/media_sound.dart`. Tiles show a "Video" badge instead of autoplaying (grids would run several decoders at once).
- **Drops** (`modules/drops`): shoppable videos/photos. Videos stay `PROCESSING` until Cloudinary's signed webhook (`/api/v1/media/cloudinary/notify`, raw body, mounted before `express.json`) or the scheduler confirms the HLS rendition. Feed ranking is explainable and non-profiling (freshness, engagement, distance, rating; `RANKING_EXPLANATION`, DSA Art. 27) with a snapshot cursor for stable paging; `latest` is chronological. Likes are unique per user, views are de-duplicated per viewer per day (`DropView`). Reports (DSA Art. 16) auto-hide a drop after three distinct signed-in reporters; admin removal requires a reason and emails the store a statement of reasons. Public share pages at `/d/:id`. **Photo drops with sound** (since 2.13.0): an IMAGE drop has up to 10 photos (`upload` + `images[]` ≤ 9 → `Drop.extraImagePublicIds`, in order) and an optional sound track the store uploads (`audio`, media kind `drop_audio` = Cloudinary audio under the `video` resource type, mp3/m4a/aac/wav/ogg/opus/flac, ≤ 90 s → `audioPublicId`/`audioDurationSec`, delivered as MP3 via `lib/cloudinary.ts#audioMp3Url`); a VIDEO drop plays its own sound and refuses `images`/`audio` (400). Payload `media {images[], image (first), audio {url, durationSec} | null}`; deleting a drop erases every photo and the sound. Store app `create_drop.dart` (pick several photos, add/listen/remove a sound file, licence note on music); customer `drops_feed.dart` plays the sound through the same controllers and `MediaSound` switch as videos and shows the photos as `_PhotoSlideshow` (3.5 s auto-advance while playing, swipe sideways, dots). **Reels tools** (since 2.14.0, `modules/sounds`): a **sound library** of tracks Malvoya holds a licence for (`Sound`: title, artist, licence text + URL, active; upload kind `library_sound`, admin only, ≤ 180 s; `GET/POST/PATCH /admin/sounds`, audited `sound.create|update`, admin panel → Sounds). Stores pick from `GET /sounds?q&before` (active only); `GET /sounds/:id` + `/sounds/:id/drops` are the public sound page; `useCount` is counted on read. Stores' own sounds are never shared. `POST /drops` takes `soundId` (library) **or** `audio` (own file or a voice-over recorded in the store app with `record` 6.x, kind `drop_audio`) on video and photo drops, `soundMode` MIX|REPLACE for videos (default MIX), and `trimStartSec`/`trimEndSec` for videos (≥ 3 s window; playback trims, the file is not cut). Payload `media.audio {url, durationSec, sound {id,title,artist}|null, mode}` and `media.trim {startSec, endSec}|null`. Viewers: `PUT/DELETE /drops/:id/save` (`DropSave`, `saveCount`, `savedByMe`, `GET /me/saved-drops`) and `POST/DELETE /drops/:id/not-interested` (`DropHide`: hidden from that user's feeds, store and sound lists); both in data export, deleted with the account. Customer app: added sound plays in a second controller in step with the video (video volume 0.3 MIX / 0 REPLACE, × `MediaSound`), trim loop, `_ReelProgress`, Save in the rail, long-press sheet (Save, Not interested with Undo, Share, Report; holding pauses), `screens/sound_screen.dart`, `screens/saved_drops_screen.dart` (Profile → Saved drops), `widgets/drop_grid.dart`. Store app: `screens/drop_sound_sheet.dart` (Library / Your file / Voice-over), mix/replace choice and a trim RangeSlider in `create_drop.dart`. Comments and follows live in `modules/drops/social.ts`: comments are plain text up to 300 chars (20 per user per 10 min), shown with the first name only (the posting store's own replies show as the store), deletable by the author, the store or an admin, and hidden after three distinct reports until an admin decides (admin panel → Moderation → Reported comments). `Drop.commentCount` counts VISIBLE comments only. Following a store adds its drops to the `following` feed mode (chronological) and sends followers a push when a drop goes live (`notifyFollowers`). Account deletion removes the user's comments and follows. `pushToUsers` sends in batches of 500 tokens (FCM limit).
- **Live shopping** (since 2.15.0, `modules/live`, `lib/livekit.ts`): stores stream from the store app's camera over LiveKit (WebRTC); nothing is recorded. Off without `LIVEKIT_URL`/`LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` (503 `LIVE_OFF`; `GET /live` → `{enabled:false}`); tokens are HS256 JWTs signed with `jsonwebtoken` (publisher `store-<id>`, viewers `u-<id>`, ≤ 6 h), no LiveKit SDK on the server. `LiveStream` (title, 1–10 own products, pinned product, LIVE|ENDED, heartbeat, viewers/viewerPeak/likeCount, `endedReason` store|timeout|max_duration|admin), `LiveMessage` (≤ 200 chars, hidden flag; purged 30 days after the end by `live-chat-purge`, deleted with the account, in export), `LiveBan`, `LiveReport`. `POST /live` (approved store, 428 agreement; 409 `ALREADY_LIVE` with a fresh `publish`; ≤ 10/day; followers pushed at most once per 6 h) → `{live, publish {url, token}}`; `POST /live/:id/{heartbeat,pin,end,publish}`; the `live-watchdog` ends lives without a heartbeat for 2 min or after 4 h. Public `GET /live?lat&lng`, `GET /live/:id` (`shareUrl`, products), `POST /live/:id/join` → `{watch}`, `GET /live/:id/messages` (blocked authors left out), `POST /live/:id/report`; `GET /stores/my/live`. Sockets (signed in): `live:join` (ack with viewers, likes, pinned, messages), `live:leave`, `live:chat` (10/min), `live:like`, store/admin `live:hide`, `live:ban`; server emits `live:message|viewers|likes|message_hidden|pinned|ended`. Viewers are counted from sockets in `live:<id>` (Redis-safe; the store's own sockets excluded). Admin: `GET /admin/live`, `/admin/live/:id/messages`, `POST /admin/live/:id/end {reason ≥ 10}` (audited `live.end`, statement of reasons by email + push), `POST /admin/live/reports/:id`; admin panel → Live; System lists LiveKit and Test connections calls ListRooms. Apps: customer Drops tab "Live" mode (`widgets/live_list.dart`) and `screens/live_screen.dart` (`livekit_client`, chat, hearts, pinned product, products sheet, report); store app `screens/live/` (set-up with products and camera preview, live screen with chat moderation, pin, flip, mute, heartbeat, `wakelock_plus` held below 1.8 because 1.8 needs Flutter 3.44).
- **Pricing** (`modules/products/pricing.ts`): every sale price is recorded in `PriceChange`. A "was" price is shown only when it is the lowest price of the 30 days before the latest reduction (Omnibus); never compute discounts in the apps. Public products expose `inStock` flags, not stock counts. Products with options (`ProductVariant`) keep `stockQuantity` = sum of option stock.
- **Payouts** (`modules/payouts`): Stripe Connect Express. On `DELIVERED`, `createPayoutsForOrder` makes a courier payout (released now) and a store payout (released after `storePayoutHoldDays` = 15). `processDuePayouts` transfers with an idempotency key per payout and ties a transfer to the charge (`source_transaction`, `Payout.linkedToCharge`) only while the linked transfers fit in it (charge − refunds − already linked; a courier transfer also leaves room for the pending store payout); anything else is paid from Malvoya's balance. Orders whose store payout + courier pay exceed the charge are logged and counted in System → attention. Refunds before release reduce the store payout (`adjustStorePayoutForRefund`). Onboarding and KYC happen on Stripe's pages.
- **Reserve & collect** (since 2.8.0, `Order.fulfilment` `DELIVERY | PICKUP`): quote/order take `fulfilment`; PICKUP needs no address, has no delivery fee, courier pay or dispatch, refuses tips (400) and needs a store address; the quote adds `pickup {storeName, address}`. The webhook creates `Order.pickupCode` (6 random digits). Flow: accepted → `PATCH status PROCESSING` = ready (`readyAt`, push "Ready for pickup at …") → the store enters the code at `POST /orders/:id/collect {code}` (owner only; wrong code 400 `{error, attemptsLeft}`, 5 wrong → locked 15 min, `lockedUntil`) → `DELIVERED`, `handoverMethod "PICKUP"`, store payout as usual. Couriers never see pickup orders (available list, accept, dispatch, watchdog step 3). The watchdog reminds the customer at `PICKUP_REMINDER_HOURS` (24) after ready and cancels with a full refund at `PICKUP_HOLD_HOURS` (72). An accepted pickup order never marked ready is cancelled with a full refund after `PICKUP_READY_HOURS` (24) from acceptance.
- **Order payload secrets** (`lib/prisma.ts` global `omit`): `Order.pickupCode`, `referrerId` and `courierPay` are left out of every order query. Only the customer gets `pickupCode` (getOrder/list, while CONFIRMED/PROCESSING); `courierPay` only in courier views (available, mine, accept/arrive/deliver responses), dispatch offers and the admin order list. Ask with `omit: { field: false }` or `select`.
- **Unpaid checkouts** (since 2.10.0): `GET /orders/:id/payment` (owner) returns `{clientSecret, amountCents, holdUntil}` while PENDING/unpaid within `CHECKOUT_HOLD_MINUTES`, else 409. `createOrder` cancels the customer's other unpaid checkouts ("Replaced by a new checkout", no notifications) after a successful reservation, or first and retries once when the basket fails only on stock (`StockError`).
- **Store cancel reason** (since 2.10.0): `PATCH /orders/:id/status {status:"CANCELLED", reason?}` (≤ 200) from the store stores the reason as `cancelReason` (default "Declined by store") and `Order.cancelledBy = "STORE"`; the push and email show it. Analytics counts these as `store_cancelled` (own words) / `store_declined`.
- **Courier cannot deliver** (since 2.10.0): `POST /orders/:id/delivery-problem {reason: CUSTOMER_UNAVAILABLE|WRONG_ADDRESS|OTHER, note?}` (assigned courier, SHIPPED) sets `deliveryProblemAt` once (reason/note updatable), pushes customer and store, appears in System attention; returns `canReturnAt` (+10 min). From then `POST /orders/:id/return-to-store` cancels ("Customer could not be reached", `returnedToStoreAt`), restocks, refunds **items only** (subtotal − discount; delivery fee, tip, service/small-order fees kept) by a partial Stripe refund (`paymentStatus` stays SUCCEEDED), creates only the courier payout (`createCourierPayoutForReturnedOrder`: job pay + tip; no store payout), pushes both and emails the customer. `POST /orders/:id/returned-received` (store) sets `returnReceivedAt`. The "still needs a refund" and "pays out more than charged" checks know these orders.
- **Order chat** (since 2.10.0, `modules/orders/chat.ts`, `OrderMessage`): customer + assigned courier (+ admin read/write; stores excluded). `GET /orders/:id/messages` → `{messages:[{id, orderId, senderRole, senderId, text, createdAt}]}` (last 100, oldest first), `POST /orders/:id/messages {text}` (≤ 1000, 30/min, 409 once the order is closed) emits `chat:message` to `chat:<id>`; socket `chat:join` acks `{ok, messages}` and `chat:send` stores through the same function. Scheduler `chat-purge` deletes messages 30 days after delivery/cancellation; account deletion deletes the user's messages.
- **Delivery handover:** couriers complete orders only via `POST /orders/:id/deliver` (`IN_PERSON`, or `PHOTO` with a verified upload), recording the handover position; `PATCH status DELIVERED` is refused for couriers.
- **Push** (`lib/push.ts`): FCM via `FIREBASE_SERVICE_ACCOUNT`; service messages only (orders, offers, drops, payouts). Tokens in `DeviceToken`, dead tokens pruned.
- **Order watchdog** (`services/orderWatchdog.ts`, every minute): unpaid checkouts are cancelled after `CHECKOUT_HOLD_MINUTES` (30) and release their stock; a paid order the store has not answered gets one push reminder at `STORE_REMINDER_MINUTES` (3) and is cancelled with a full refund at `STORE_ACCEPT_MINUTES` (10); accepted orders without a courier are re-offered every `COURIER_REOFFER_MINUTES` (2) (`Order.lastOfferAt`), the customer hears about the delay at `COURIER_DELAY_NOTICE_MINUTES` (15) and the order is refunded at `COURIER_SEARCH_MINUTES` (45, counted from `Order.confirmedAt`). Cancellations go through `cancelOrderInternal` (idempotent, restock + refund/void).
- **Store availability** (`utils/openingHours.ts`): `Store.acceptingOrders` (the store's pause switch) and `Store.openingHours` (`{ mon: [["09:00","18:00"]], … }`, Europe/Helsinki, ranges may pass midnight, null = always open). Store responses carry `openNow`, `closedReason` (`paused`/`closed`) and `opensAt`; `createOrder` refuses closed stores with 409; open stores sort first. Set `openingHours: null` to clear (stored as DB NULL).
- **Launch alerts** (`modules/me/launchAlerts.ts`, `LaunchAlert`): "notify me when Malvoya opens near me" (`PUT/GET/DELETE /me/launch-alert`, one pinned location per user). The first approval of a store notifies everyone waiting within 10 km once (push); `GET /admin/launch-demand` groups the waiting list by area. Included in data export, deleted with the account.
- **System status** (`modules/admin/system.ts`, `GET /admin/system`, admin panel → System): which integrations are on (yes/no and Stripe test/live, never secrets), plain-language blockers for real orders, things needing a human, marketplace counts, timers, fee settings (`pricing`, including courier pay, the customer delivery-fee settings and the margin on example jobs) and last job runs. - **Email identity:** `malvoya.com` is not under our control, so nothing is sent from or to it: mail goes out as `SMTP_FROM` or the `SMTP_USER` mailbox, and support requests are emailed only when `SUPPORT_EMAIL` is set (they are always in the admin panel).
- **Tips** (`Order.tipCents`, max 20 €): added to `totalCents` and to `courierFeeCents` (so the courier payout includes it), no commission. Shown on receipts, courier offers and the courier job list.
- **Courier position freshness** (since 2.8.0, `utils/courierPosition.ts`): every position write sets `Courier.locationAt`; positions older than 2 min count as unknown (no ride pay). A courier whose fresh position is beyond `COURIER_APPROACH_MAX_KM` (7.5, the dispatch radius) cannot accept (409 "too far"), and the paid ride is capped at it. `arrived-at-store` needs a fresh position within 300 m of the shop. Waiting is paid from max(check-in, acceptance + expected ride at 15 km/h) until the store marked the order ready (`readyAt`) or pickup. Accepting or cancelling an unassigned job emits `courier:offer_closed {orderId, reason}` to the `couriers` room; offers and `GET /orders/available` carry `offeredAt`.
- **Courier pay** (since 2.7.0, `utils/courierPay.ts`, Platform Work Directive transparency): separate from the customer's delivery fee. `COURIER_PAY_MODE=formula` (default): max(`COURIER_PAY_BASE_CENTS` 450 + `COURIER_PAY_PER_KM_CENTS` 110 × route km, `COURIER_PAY_MIN_CENTS` 650) + ride to the shop beyond `COURIER_APPROACH_FREE_KM` 2 km × `COURIER_APPROACH_PER_KM_CENTS` 50 (courier's last location → shop, fixed on accept; offers/job list show a per-courier estimate) + waiting after `COURIER_WAIT_FREE_MINUTES` 5 × `COURIER_WAIT_PER_MIN_CENTS` 20, max `COURIER_WAIT_MAX_CENTS` 400 (from `POST /orders/:id/arrived-at-store`, which sets `Order.courierArrivedAt` once, to pickup; added at `SHIPPED`) + tip. Route km = straight line × `COURIER_ROAD_FACTOR` 1.3, rounded to 0.1 km. `fee_share` = the old `COURIER_FEE_SHARE` × delivery fee + tip. The breakdown is stored in `Order.courierPay` (Json); `courierFeeCents` always equals its `totalCents` and is what the payout uses. Orders without a breakdown (pre-2.7) are shown as a fixed fee. The delivery margin may be negative; `GET /admin/system` → `pricing.courierPay.examples` shows it for 1/3/6 km.

A REJECTED return is closed for the store (409; admins may reopen), a store cannot refund once its payout is PAID (support only), and the refund claims the return (`updateMany` on its status) before calling Stripe. `markOrderPaid` marks paid only a non-cancelled order (`updateMany`) and refunds a payment that arrives after cancellation; `cancelOrderInternal` decides refund vs void on the state read after cancelling. Sign-in, reset and pickup codes use up an attempt (`updateMany` with `attempts < max`) before comparing, so parallel requests get no extra guesses. Sockets: the handshake applies `sessionAllows` (active, `tokensValidAfter`, two-step), a ban or deletion disconnects the user (`disconnectUser`), a suspended courier leaves the offer rooms, and only chat members (customer, assigned courier, admin) join `chat:<id>`. **Rentals are off**: `POST /rentals` answers 410 `RENTALS_UNAVAILABLE` (stores are not notified, no payouts/deposit returns/rental returns exist) unless `RENTALS_ENABLED=true`. Indexes for the watchdog, pg_trgm search and email lookups (migration `20261027140000_search_and_watchdog_indexes`, `docs/scaling/indexes.md`). `/admin/couriers` takes 500; `/admin/support` returns `total`, open requests oldest first, others newest first.
- **Contact form** (since 2.13.0, `modules/support/contactPage.ts`): public `/contact` (fi/en, no scripts, strict CSP, 8/h per IP) → `SupportRequest` with app `web` and the topic (general, withdrawal, privacy, illegal content, seller complaint, DSA authority contact); it is the contact address in the legal texts (no mailbox on malvoya.com exists) and the DSA point of contact. System lists a blocker while any legal text in force still has `[PLACEHOLDERS]`.
- **Payout onboarding before approval** (since 2.12.0): stores and couriers can start Stripe Connect onboarding before an admin approves them (it is an onboarding step); payouts only exist for delivered jobs, which need approval.

### Scaling foundations (keep them when changing code)

- **Stateless instances:** no user state in process memory. Sign-in codes are in the `OtpCode` table. Sessions are JWT plus hashed refresh tokens in the DB. With `REDIS_URL` (optional, `lib/redis.ts`) instances share rate limits (`rate-limit-redis`, `middleware/rateLimiter.ts#rateLimitStore` — use it for new limiters), Socket.io rooms (`@socket.io/redis-adapter`; the worker emits via `@socket.io/redis-emitter`), session-cache invalidation (pub/sub in `middleware/auth.ts`), `Idempotency-Key` answers (`middleware/idempotency.ts`) and the job queue (`lib/queue.ts`, BullMQ; in-process without Redis; `WORKER_MODE=api` + `node dist/worker.js`). Without `REDIS_URL` everything is per-instance as before. All scale settings live in `config/scale.ts`; plan, costs, runbook and index recommendations in `docs/scaling/`; tests in `test/e2e/scale.e2e.js` (own DB `malvoya_scale`, ports 4565/4567/4568).
- **Indexes:** every foreign key and list query path has an `@@index` (migration `20260925090000_scale_indexes_and_otp`). Add one whenever you add a new `where`/`orderBy` path.
- **List endpoints are bounded** (`take` limits, paginated store and product lists). Never return unbounded lists.
- **Operations:**
  - `/health` is liveness and `/health/ready` checks the database and Redis (503 while draining); `GET /api/v1/admin/metrics` (admin or `METRICS_TOKEN`) shows event-loop lag, heap, pool, per-route p50/p95/p99 (also logged every 5 min), sockets, queue. Optional Sentry (`SENTRY_DSN`, PII scrubbed in `lib/sentry.ts`).
  - Graceful SIGTERM shutdown enables zero-downtime deploys.
  - `pino-http` logs one line per request with an `x-request-id`; auth headers are redacted, and bodies and PII are never logged.
  - `compression` is on.
  - The pg pool (`lib/prisma.ts#pgPool`) is `DB_POOL_MAX` (default 10) per instance, with `DB_STATEMENT_TIMEOUT_MS` (30 s) and an idle-in-transaction timeout.
  - Public GETs get Cache-Control/ETag (`middleware/httpCache.ts`; signed-in = private). Order/rental/return lists take optional `?limit=&before=` and return `nextBefore`.

The simulated escrow, dispatch engine, telemetry service, "AI garment inspection" (RaaS/MCP) and BullMQ worker were deleted in September 2026 because they faked behaviour. Also removed from the apps: invented discounts/likes/sizes in the feed, locally-stored "drops", fake GPS proof, VoIP/SMS relays, fake support tickets and guarantees, keyword bots labelled "AI", pre-ticked consent switches for tracking that does not exist, and hard-coded delivery fees/ratings. Don't restore them from git history.

## Flutter app conventions

- Shared per-app helpers in `lib/core/`: `api_client.dart` (session, one retry after refresh, user-readable errors — use it for new calls instead of raw `http`), `push_service.dart` (FCM token registered after sign-in, removed via `AuthService.beforeLogout`), `strings.dart` (`tr(context, en, fi)` for new copy, `euro()`), `legal_links.dart`, and in store/courier `media_upload.dart` (signed direct uploads with progress).
- Customer: `DeliveryLocation` (pinned coordinates of the active address) drives store ranking, fees and ETAs and is sent with orders; the Drops tab (`screens/drops_feed.dart`) preloads ±1 HLS videos and reports views; `screens/catalogue.dart` is the search; `screens/order_detail.dart` is live tracking. Map tiles are OpenStreetMap (never scrape Google tiles).
- Courier: `CourierTelemetryService` shares position only while online, through an Android foreground service (visible notification); `setActiveOrder` ties it to the carried order.
- Each app has `lib/auth_service.dart` built from one shared design. `kAppRole` is set per app, and accounts with another role are refused at sign-in. Tokens live in `flutter_secure_storage`. The access token is refreshed automatically a minute before it expires. Phone sign-in = Firebase verifies the SMS code, then the Firebase ID token is exchanged at `/auth/phone`. Never derive passwords or fake sessions on the client.
- The apps never ask the server to send messages, and never report success for something the server rejected (no "saved locally" fallbacks).
- Every app lets the user delete the account in-app (Play requirement): customer via Privacy → Delete account, store and courier via `core/delete_account_tile.dart`. Courier location sharing is stopped by an `AuthService.beforeLogout` hook, so it ends with any sign-out. Profile name changes go through `PATCH /me/profile`.
- Payments: the customer app only opens Stripe's PaymentSheet with the server's `clientSecret`. On Android `MainActivity` must stay a `FlutterFragmentActivity` with Material (AppCompat) themes in `res/values*/styles.xml`, or flutter_stripe refuses to start and no payment opens. **Never add card, CVV or IBAN input fields**; that would put the app in PCI-DSS scope.
- State: `provider` `ChangeNotifier`s. (The unused `features/order_tracking` bloc module with invented fallback data and the unused `screens/otp_verification.dart` were deleted in 2.15.) Localization is hand-rolled `AppLocalizations` in `Malvoya_customer/lib/l10n.dart` (fi/en). New user-facing copy is written as "Finnish / English".

## Compliance context (Finland / EU)

GDPR: data minimisation, retention, export and delete are implemented. Hosting is in Frankfurt (EU). The Accounting Act requires keeping order records. The Consumer Protection Act chapter 6 gives a 14-day withdrawal right and a refund of the delivery fee. PSD2 SCA is handled by Stripe. The Platform Work Directive (from Dec 2026) requires transparent, non-automated courier management. DAC7 requires seller reporting. Omnibus: `Store.sellerType` (BUSINESS/PRIVATE, with Y-tunnus for businesses) is shown to shoppers and locked after verification; "was" prices follow the 30-day rule; reviews are verified purchases. DSA: notice-and-action, statements of reasons, trader information on product and store pages, recommender transparency. No Y-tunnus exists yet, so never invent company names or business IDs. Legal texts in `legal/` use `[PLACEHOLDERS]`.
